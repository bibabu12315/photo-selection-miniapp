## 方案评审结论（关键技术判断，待用户确认）
1. **原图不上云**：300 张 × 18MB ≈ 5.4GB 上传不现实。original 层改为「可选备份 / 延后」，V1.0 只传 preview + thumbnail（约 160MB）。原图始终留在摄影师本地。
2. **图片派生放前端**：wx.compressImage / canvas 压缩 + 画水印，避免云函数处理大图（超时/内存）。注意 canvas 重绘会丢 EXIF 方向。
3. **选图数量限制**：wx.chooseMedia / chooseImage 单次上限 9 张 → 必须分批累积到上传队列，或另开电脑端上传入口。
4. **小程序码 scene ≤32 字符**：与「高熵 token」冲突 → token 用 22 位 base62（约 131 bit），二维码只放 token；另建议支持「分享小程序卡片」直发给模特。
5. **免注册权限方案**：管理员 openid 硬编码 → 摄影师端；模特静默 wx.login 拿 openid，selection 绑定 openid。
6. **尺寸建议**：preview 长边 2048（约 400-700KB），thumbnail 长边 400（约 30KB）。方案原写 2400-4000 偏大。
7. **selection 数据结构**：建议 project 级文档 + selectedPhotoIds 数组，而非 300 条独立文档，减少写入与同步复杂度。
8. **精修匹配**：V1.0 用「点选已选照片 → 上传对应精修图」，比盲目按文件名批量匹配更稳。

## 平台硬限制（已核实）
- 小程序是沙箱，FileSystemManager 只能访问自身目录，**无法读取 SD 卡 / OTG / 读卡器 / U 盘**。
- `wx.chooseMedia` / `chooseImage` count 上限 9；`wx.chooseMessageFile` 只能从微信会话选，上限 100，无文件夹概念。
- **web-view 组件个人主体小程序不可用**（业务域名不开放给个人类型）。但**电脑端独立浏览器 H5 不受此限制**。
- 因此「手机端直接读读卡器」在小程序内无解；只能电脑端，或手机文件 App 多选 → 分享到文件传输助手 → chooseMessageFile。
- CloudBase Web SDK 上传：需登录态（可用匿名登录 anonymousAuthProvider），需配置「安全域名」（CORS）；存储权限设「仅创建者可读写」即可满足私有要求，云函数用 admin 权限读。

## 安全设计（用户提问：无登录体系，模特 B 能否看到模特 A 的图）
结论：隔离靠 token 不靠账号，但**四道锁必须做对**：
1. **数据库权限设「仅管理端可读写」**（最大的漏洞——默认「所有用户可读」会让 token 形同虚设，前端一句 db.get() 就能拿全部项目）
2. **每次下发图片链接前校验 token 推导出的 projectId 与请求参数一致**（参数里的 projectId 永远不能信）
3. **管理员绑定不能自动绑定**（上一版写的"第一个打开的人自动绑定"有漏洞：模特先打开就会被绑成管理员）→ 改为环境变量 `ADMIN_BIND_KEY` 口令绑定（方案A）或 `ADMIN_OPENID` 硬编码（方案B）
4. **一码一人**：selection 记录 boundOpenid，首次进入写入，之后不同 openid 拒绝；管理员 openid 放行；摄影师端可解绑。约 20 行代码，替代登录体系。
防不住的三项（发错码、码发群里、截图外传）属人为而非技术问题。建议优先用分享卡片而非二维码图片。
四道锁合计 <100 行代码，**不需要做账号体系**。

## Phase 2 存储上传失败排查（OPERATION_FAIL[storage]）
- 根因：Web SDK 在微信云开发环境只有「未登录模式」（拿不到登录态，auth == null），而存储权限是简易权限「仅创建者可读写」——未登录用户必须搭配安全规则才能访问存储，简易权限直接拒绝
- 解法：存储 → 权限设置 → 改「自定义安全规则」→ {"read": false, "write": true}（只许写不许读，保持私有；下载走云函数 admin 临时链接）
- 已提醒：write: true 意味着任何匿名者可写文件（不可读），V1.0 可接受，靠 photo 云函数会话 token 保障登记安全
