## 一、四道锁（V1 已有三道，V2 新增第四道）

| # | 锁 | 作用 | 位置 |
|---|---|---|---|
| 1 | **数据库仅管理端可读写** | 小程序端与网页端都无法直接读写任何集合，必须走云函数 | 云开发控制台 · 数据库权限 |
| 2 | **存储「仅创建者可读写」** | 图片 fileID 本身不可被外部直接下载，必须由云函数换临时链接 | 云开发控制台 · 存储权限 |
| 3 | **一码一人** | 邀请链接首次被某微信打开后即绑定 openid，换人打开拒绝 | `selection.entry` |
| 4 | **sessionToken**（V2 新增） | 网页端凭票据换来的会话令牌，30 天有效，可登出撤销 | `session` 集合 |

**四道锁的关系**：前三道保证「外人拿不到数据」，第四道解决「网页端如何证明自己是摄影师」。
第四道是**新增的攻击面**，必须按第三节的规则实现，不能简化。

## 三、`resolveCaller` 的实现规则（V2 核心）

### 3.1 判定顺序（不可调换）

```
1. 若 cloud.getWXContext().OPENID 存在 → 直接用它（小程序路径）
2. 否则取 event.sessionToken → 查 session 集合 → 换 openid（网页路径）
3. 都取不到 → 返回 ''，调用方拒绝请求
```

**为什么小程序路径优先级更高**：防止网页端构造请求时混入 sessionToken 尝试提权。
只要请求真的来自小程序，就以微信签发的 OPENID 为准。

### 3.2 必须满足的校验

```js
// session 查询条件，四条全中才算有效
where({
  token: token,
  status: 'ACTIVE'
})
// 且
s.expireAt > Date.now()          // 或 tokenExpireAt > now
// 且
s.openid 非空
```

**禁止**：
- ❌ 用 `where({ token })` 而不校验 `status`（登出后 token 仍能用的漏洞）
- ❌ 不校验过期时间
- ❌ 把 openid 返回给网页端以外的任何地方（网页端只存 token，不存 openid）
- ❌ 在客户端做任何「是不是摄影师」的判断（客户端判断只能用于 UI 展示，服务端必须再判一次）

### 3.3 双重校验

`resolveCaller` 只解决「你是谁」，**每个 action 还要再判「你有没有资格对这个资源操作」**：

| 场景 | 第二重校验 |
|---|---|
| `project.*`（除 create/list） | `ownedProject(id, openid)` —— `ownerOpenid` 必须匹配 |
| `project.create` | `isAdmin(openid)` |
| `selection.getResult` / `resetLock` / `getProjectResults` | `isAdmin(openid)` |
| `selection.getPhotos` / `getPreview` / `saveSelection` | `guardModel(projectId, modelId, openid)` |
| `photo.issueUploadSession` | `isAdmin + ownedProject` |

> **不要因为「resolveCaller 已经确认了身份」就跳过第二重**。
> 身份认证 ≠ 资源授权，这两件事必须分开做。

## 四、令牌规则

| 令牌 | 长度 | 字符集 | 有效期 | 生成 | 出现位置 |
|---|---|---|---|---|---|
| `invite.token` | 22 | base62 | 长期（项目存续期） | 服务端 `randomBase62` | 小程序码 scene、邀请链接 |
| `session.ticket` | 22 | base62 | **5 分钟** | 服务端 | 小程序码 scene（可被拍照传播，故短命） |
| `session.token` | 32 | base62 | **30 天** | 服务端 | 仅存 localStorage，**绝不出现在二维码/URL 中** |
| `project.uploadToken` | 22 | base62 | 24 小时 | 服务端 | 网页内存 |
| `project.uploadCode` | 6 | 数字 | 5 分钟 | 服务端 | 摄影师手工输入 |

**生成规则（禁止自创）**：一律用服务端 `crypto.randomBytes` + base62 编码。
**禁止**用时间戳、自增 ID、`Math.random()`、openid 哈希等可推导值。

**ticket 与 token 分离的理由**：ticket 会被印在二维码里（可能被拍照、被转发），token 不会。
即使 ticket 在 5 分钟内泄露，攻击者仍需用**受害者的微信**扫码才能兑换 token。

## 五、已知的安全妥协（接受，并明确记录）

| 妥协 | 原因 | 缓解 |
|---|---|---|
| **邀请链接可被转发** | 微信无法限制链接传播 | 一码一人（第三个微信打开会被拒）；项目到期自动归档 |
| **模特可截屏** | 小程序无法禁截屏（且红线禁止做防截屏） | 只上传 preview 不上传原图，截屏拿到的只是低清预览 |
| **sessionToken 存 localStorage** | 网页端无更安全的存储 | 30 天过期；提供登出；不存 openid |
| **零门槛开通摄影师** | 决策 R-5，降低使用门槛 | 隔离靠 `ownerOpenid`，开通本身不泄露他人数据 |
| **上传会话 24h** | 上传一批照片可能需要很久 | 仅对单个项目有效，且与项目绑定 |

> 以上均已权衡后接受。**不要**在 V2 中自行「加固」（例如加防截屏、加登录密码、加短信验证），
> 那属于范围外变更。

## 六、存储权限（与 `24_FILE_STORAGE.md` 配合）

- 云存储权限：**仅创建者可读写**（即只有云函数用 admin 身份能读）
- 因此**所有图片 URL 都必须由云函数 `getTempFileURL` 下发**，且带有效期
- V2 明确**不改**这条权限（曾评估过「改公开读 + fileID 直出」以减少调用，
  但那会让链接可被无限转发，收益不抵风险 → 见 `docs/云成本优化-四项技术任务.md`）

## 七、V2 安全检查清单（上线前逐条验证）

- [ ] 全部 7 个集合权限为「仅管理端可读写」
- [ ] 云存储权限为「仅创建者可读写」

- [ ] 已提交锁定的模特再调 `saveSelection` → 返回 `ERR_LOCKED`
- [ ] 邀请链接换第三个微信号打开 → 被拒绝
- [ ] 小程序端调用不受影响（回归首页/选片/提交/结果）
- [ ] 网页端控制台不出现任何 openid 明文（检查 localStorage 与网络请求体）

## 八、禁止事项

1. **禁止**在小程序端或网页端直接调用 `db.collection(...)`——数据库权限已禁止，写了也跑不通，不要尝试绕过
2. **禁止**把 openid 写入 localStorage / URL / 日志
3. **禁止**为了方便调试而临时关闭 `isAdmin` 校验（要临时测试请用真实的摄影师微信号）
4. **禁止**新增任何「口令」「密钥」作为鉴权手段（V1 已砍掉摄影师口令，不再复活）
5. **禁止**实现防截屏、水印、设备管理（红线）
