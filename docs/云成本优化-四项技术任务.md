# 云成本优化 · 技术任务清单

> 给执行者（另一个会话的 AI / 未来的自己）照着改。
> 配套文件：`docs/成本与定价测算.html`（改完可以回测算器把四项开关打开，看数字变化）。
> 本文档只描述"改哪里、改成什么、怎么验收"，不含定价讨论。

---

## 0. 为什么要做

按当前代码的资源耗率，一个满额度的专业档用户月成本约 19 元，卖 9.9 是倒挂的；做完下面这些改动后降到约 5.6 元，毛利率回到 43%。**定价能不能成立，取决于这套改动做不做。**

当前基线（单张照片的完整生命周期）：

| 项 | 现状 | 目标 |
|---|---|---|
| preview 体积 | 2048 / q82 ≈ 0.55 MB | 1600 / q75 ≈ 0.25 MB（默认档） |
| thumbnail | 480 / q75 ≈ 0.04 MB | 320 / q70 ≈ 0.025 MB |
| 云调用次数 | 约 17 次/张 | 约 8 次/张 |
| 归档后单张占用 | 0.59 MB（等于没归档） | 0.025 MB（只留 thumb） |

## 1. 优先级说明

| 级别 | 任务 | 不做会怎样 |
|---|---|---|
| **P0** | 删除/归档项目时清理云存储 | 容量只增不减，几个月后必然撑爆 2GB |
| **P0** | `usedBytes` 在线额度计数器 | 在线额度只是个数字，没有真实计量就收不了加量包的钱 |
| **P1** | 四项优化 | 毛利率从 43% 掉到 -93%，卖一单亏一单 |
| **P2** | 画质档位开放给前台 | 专业档"更高清"卖点无法兑现 |

## 2. P0 · 容量治理

### 2.1 删除项目时必须同时删云存储文件（现在是泄漏的）

- **落点**：`cloudfunctions/project/index.js:139` `removeProject()`
- **现状**：全项目搜索 `deleteFile` **零命中** —— 删项目只删数据库记录，云存储上的 preview / thumbnail 永久残留。这是纯粹的成本泄漏，用得越久漏得越多。
- **改法**：在 `removeProject()` 删数据库记录之前，先把该项目的图片文件删掉。

```js
// 1) 取出该项目的所有图片（只取 fileID 两个字段，不要整文档）
const ps = await db.collection('photo').where({ projectId: id }).field({ previewFileID: 1, thumbFileID: 1 }).limit(1000).get()
const fileIDs = []
ps.data.forEach(p => { if (p.previewFileID) fileIDs.push(p.previewFileID); if (p.thumbFileID) fileIDs.push(p.thumbFileID) })
// 2) 分批删除，deleteFile 单次上限 50
for (let i = 0; i < fileIDs.length; i += 50) {
  await cloud.deleteFile({ fileList: fileIDs.slice(i, i + 50) })
}
// 3) 再删 photo / selection / invite 记录，最后删 project
```

- **注意**：`photo` 集合一次最多取 1000 条，超过要循环翻页；删除失败不能阻断主流程，用 try/catch 包住并把失败 fileID 记到日志。
- **验收**：删一个项目 → 云开发控制台「存储」容量立刻下降；再查 `photo` 集合确认记录也清了。

### 2.2 项目到期改为「归档」，不是删除

- **落点**：`cloudfunctions/project/index.js:173` `extendProject()`、`:93` `status: 'DRAFT'`、状态机里的 `EXPIRED`。
- **现状**：已有 `expireAt` 与 `EXPIRED` 状态，但过期后没有任何自动动作，文件一直占着。
- **改法**：新增一个 `archiveProject(id)` 分支，做三件事：
  1. 删掉该项目所有 `previewFileID`（**保留** `thumbFileID`）；
  2. 把 project 状态置为 `ARCHIVED`，保留 `name / 模特 / 已选文件名列表`；
  3. 把 `usedBytes` 减去已释放的部分（见 2.3）。
- **触发方式二选一**：
  - 云函数定时触发器（`cloudfunctions/project/config.json` 加 `triggers`，每天跑一次，扫 `expireAt < now && status !== 'ARCHIVED'`）；
  - 或者不做定时，在摄影师下次打开项目列表时惰性触发（实现简单，推荐先做这个）。
- **验收**：归档后摄影师仍能在列表里看到该项目和缩略图墙、能看到当时选了哪些文件名；点进大图时提示"已归档，如需重新选片请续期"。控制台容量应降到只相当于 thumbnail 的量（原本的 4% 左右）。

### 2.3 `usedBytes` 在线额度计数器

- **落点**：`cloudfunctions/project/index.js:71` `createProject()`（新增字段）、`cloudfunctions/photo/index.js:152` 写入 photo 处（累加）、2.1/2.2 的删除与归档处（扣减）。
- **现状**：项目上没有任何字节数字段，在线额度无从计量。
- **改法**：
  - project 文档增加 `usedBytes: 0`（创建时置 0）；
  - 上传成功一张后：`usedBytes += previewBytes + thumbBytes`（web 端上传时要带上这两个体积，见 4）；
  - 归档时 `usedBytes` 减去 preview 部分，删除时清零；
  - 摄影师账号层（后续做订阅时）再维护一个 `onlineBytes` = 所有未归档项目的 `usedBytes` 之和。
- **验收**：上传 100 张后查 project 文档，`usedBytes` ≈ 100 × (preview + thumb)；归档后应只剩 thumbnail 部分。

## 3. P1 · 四项优化

### 3.1 减少 `getTempFileURL` 调用（原"image 直用 fileID"）

> **这里有一个和你现有安全模型冲突的地方，先看完再动手。**

`安全与访问控制.md:42`（已移入 `docs/_archive/`，V2 版见 `23_PERMISSION.md`）写明：云存储是「仅创建者可读写」，链接由云函数以 admin 权限下发。而小程序 `<image src="cloud://...">` 直出 fileID 要求文件对当前用户可读，两者不能同时成立。

- **方案 A（破坏现有权限，不推荐单独做）**：把存储权限改成「所有用户可读」，wxml 里直接绑 fileID（`miniprogram/pages/client-select/index.wxml:43` 等三处 `<image>`）。调用降到 0，代价是任何拿到 fileID 的人都能看图，四道锁少一道。
- **方案 B（推荐，安全无损）**：保持私有权限，压调用频次：
  1. **批量**：`cloudfunctions/selection/index.js:502` 的 `tempUrls()` 已经是 50 个一批，确认 `getPhotos()`（:209）走的是它，不要退化成单张；
  2. **缓存**：小程序端把取到的 `tempFileURL` 连同过期时间写进 `wx.setStorage`，同一项目 2 小时内重复打开直接读缓存，不再请求；
  3. **加大 maxAge**：下发临时链接时把 `maxAge` 设到 24 小时（默认较短），让缓存真正有用。

- **验收**：同一项目第二次打开，抓包/看控制台调用次数应接近 0 增长。
- **我的建议**：选 B。除非你愿意接受图片链接可被转发，否则不要为了省这点钱拆安全锁。

### 3.2 `getPreview` 预取相邻 ±2 张

- **落点**：`cloudfunctions/selection/index.js:244` `getPreview()`
- **现状**：每点开一张大图就单独请求一次，返回单张链接。模特左右滑动看 100 张 = 100 次调用。
- **改法**：改成 `getPreview({ projectId, modelId, photoId, range: 2 })`，一次返回当前张 + 前后各 2 张（共 5 张）的临时链接，小程序端把这 5 条塞进缓存。滑动时先查缓存，命中就不请求。
- **验收**：连续滑 20 张，云函数调用增长应 ≤ 5 次而不是 20 次。

### 3.3 归档只删 preview（已在 2.2 覆盖）

这一项就是 2.2，两者是同一件事：归档 = 删 preview + 留 thumb。**收益最大的一项**：归档后单张占用从 0.59MB → 0.025MB，省 96%。不做 2.2 的话，第 3 项优化等于没做。

### 3.4 thumbnail 降规格

- **落点**：`web/upload.js:17` `THUMB_LONG_EDGE = 480`、`:18` `THUMB_QUALITY = 0.75`
- **改法**：改成 `320` / `0.70`。thumbnail 只用于网格列表，手机上格子通常不到 120px 物理宽，320 长边绰绰有余。
- **验收**：单张 thumbnail 从 ~40KB 降到 ~25KB；网格列表肉眼看不出区别。

## 4. P2 · 画质档位落地（专业档的卖点）

现在只有两档，且默认就是最贵的那档。

- **现状**：
  - `web/upload.js:21-24` `PRESETS = { standard: 2048/0.82, hd: 2880/0.9 }`
  - `miniprogram/env.ts:15-16` 同名预设
  - `cloudfunctions/project/index.js:94` 创建项目时 `previewSpec` 默认写死 `standard / 2048 / 82`
  - `web/index.html:68` quality 滑块范围 40–95，`web/upload.js:397` 再 clamp 到 40–95

- **目标档位表**（四档，前台只显示档位名，不显示 MB）：

| 档位名 | 长边 / quality | preview 体积 | 开放给 |
|---|---|---|---|
| 标准 | 1600 / 75 | ~0.25 MB | 全部（**新默认**） |
| 高清 | 2048 / 82 | ~0.55 MB | 免费 + 标准的上限 |
| 高清Pro | 2880 / 90 | ~1.2 MB | 仅专业 |
| 原画质 | 4096 / 92 | ~2.2 MB | 仅专业 |

- **改法**：
  1. 把 `web/upload.js` 的 `PRESETS` 扩成四档，同步 `miniprogram/env.ts`；
  2. **默认档改 `standard` 且参数降到 1600/75** —— 这是单条最大的成本杠杆，存储 + CDN 直接砍一半；
  3. `cloudfunctions/project/index.js:94` 的默认 `previewSpec` 同步改；
  4. 上传时把 `previewBytes / thumbBytes` 一并写入 photo 文档（2.3 的 `usedBytes` 依赖它，现在没有这个字段）。

- **关于「原画质」**：不要开到 q95。2.8MB/张时一个 500 张项目要 1.4GB，模特端一次浏览要下 560MB —— 不是你贵，是模特的手机先崩。4096 / q92 是"接近原画质"和"还能用"的交点。

- **验收**：四档各传同一组 20 张照片 → 控制台看存储增量，应大致落在上表的倍数关系上（标准 : 高清 : Pro : 原画质 ≈ 1 : 2.2 : 4.8 : 8.8）。

## 5. 验收总清单（全部改完后逐条打勾）

| # | 验收动作 | 通过标准 |
|---|---|---|
| 1 | 建项目 → 传 100 张 → 删项目 | 云端容量回到建项目前的数值 |
| 2 | 建项目 → 传 100 张 → 触发归档 | 容量降到只剩 thumbnail（约原来的 4%）；摄影师仍看得到缩略图和已选文件名 |
| 3 | 查 project 文档 | `usedBytes` 有值，且等于所有未归档图片的 preview + thumb 之和 |
| 4 | 模特端进相册，连续滑 20 张 | 云调用增长 ≤ 5 次 |
| 5 | 同一项目隔 1 小时再打开 | 不再请求临时链接（走缓存） |
| 6 | 同一组照片用四档各传一次 | 存储增量符合 1 : 2.2 : 4.8 : 8.8 的倍数 |
| 7 | 回到测算器，把四项开关全勾上 | 云账单下降、净利上升，且没有任何档位显示"倒挂" |

---

## 6. 建议执行顺序

1. **2.1 删除清文件**（半天，纯收益无副作用，先做）
2. **4 画质四档 + 默认降到 1600/75**（半天，收益最大的一条）
3. **3.4 thumbnail 降规格**（10 分钟）
4. **2.3 usedBytes 计数器**（半天，收钱的前提）
5. **2.2 归档 + 3.3**（一天，收益第二大的一条）
6. **3.1 + 3.2 调用优化**（一天，收益第三）

按这个顺序，每做完一步都能在测算器里看到数字变化，不用等到最后才知道有没有用。

## 7. 两个别忘了的提醒

- **当云账单月超额费持续超过 40 元时，就该比对更高档套餐了**，别一直挂着按量计费。拐点大约在 20~30 个重度用户。
- **iOS 端小程序内虚拟支付是被禁的**。摄影师 iPhone 占比很高，收款路径要么走站外（微信转账 / 收款码），要么只做年付。这个跟技术改动无关，但决定你什么时候需要去办个体户。
