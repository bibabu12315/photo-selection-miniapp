# 40 · AI 开发规则（Coding Agent 执行宪法）

> **本文档是最高优先级的执行约束。**
>
> 任何 Coding Agent（无论哪个模型、哪个会话）在动本项目代码之前，**必须先完整阅读本文档**，再阅读 `41_CODING_RULES.md`，然后按 `42_DEV_TASKS.md` 领取任务。
>
> 本文档不描述「做什么产品」，只规定「怎么做事」。

---

## 一、十一条铁律

| 编号 | 规则 | 违反后果 |
|---|---|---|
| **AI-1** | **先读完文档，再动代码。** 开工前至少读完 `40`、`41`、`42` 三份；实现具体功能前，再读该功能对应的编号文档。 | 严重：会基于错误假设写代码 |
| **AI-2** | **修改前先分析现有实现。** 必须先用 Read / Grep 确认目标文件的当前内容和行号，禁止凭文档印象直接改写。文档可能落后于代码。 | 严重：覆盖他人改动、改错位置 |
| **AI-3** | **禁止无需求重构。** 不在任务范围内的代码，一行都不许动——包括「顺手格式化」「顺手改个变量名」「这个写法不太好我优化一下」。 | 严重：产生无法 review 的巨型 diff |
| **AI-4** | **禁止擅自增加功能。** 只做任务里写的功能。想到更好的点子，写在回复里建议，**不要写进代码**。 | 严重：功能漂移、范围失控 |
| **AI-5** | **禁止擅自修改产品规则。** 产品规则 = `30_BUSINESS_RULES.md` + `00` 文档中的 R 决策 + `01_PRODUCT_SCOPE.md` 的功能清单与红线。觉得规则不合理，上报，不改。 | 致命：整套文档的权威性失效 |
| **AI-6** | **优先复用现有代码。** 已有函数/组件/样式能用的，必须复用。新增前先搜索确认「确实没有」。 | 中：重复实现，两套逻辑分叉 |
| **AI-7** | **一次只完成一个明确任务。** 从 `42_DEV_TASKS.md` 领一个 T-xx，做完、自测、汇报，再领下一个。禁止同时铺开多个任务。 | 中：中途失败时无法回滚 |
| **AI-8** | **改完必须汇报。** 每次改动后按第五节模板输出「改了什么 / 改了哪些文件 / 为什么 / 是否影响现有功能 / 是否需要测试」。 | 中：用户无法判断进度 |
| **AI-9** | **文档与代码冲突，必须上报，禁止自行猜测。** 按第四节模板输出，等待确认后再继续。 | 致命：可能推翻已确认的产品决策 |
| **AI-10** | **禁止触碰红线。** `01_PRODUCT_SCOPE.md` 第八章列出的任何一项（支付 / 二销 / AI 修图 / 精修交付 / 原生 App / Electron / 即拍即传 / 团队账号 / 防截屏水印 / 自建服务器 / 引入新框架 / 重写现有云函数），一旦出现在你的实现计划里，**立即停止并上报**。 | 致命：项目定位被污染 |
| **AI-11** | **禁止在代码中另写一份常量。** 所有常量以 `30_BUSINESS_RULES.md` 第一章为准。需要新常量，先上报。 | 中：两处常量不一致导致静默错误 |

## 二、文档优先级（冲突时的裁决顺序）

```
①  40 本文档（执行规则）
②  30 业务规则（BR-xxx）      ← 产品规则的最高来源
③  00 决策记录（R-1 ~ R-10）
④  01 产品范围（功能清单 F-xx + 红线）
⑤  31 状态机 / 32 异常处理
⑥  20~24 技术设计（架构 / 数据库 / API / 权限 / 文件存储）
⑦  10 页面规格 / 11 交互规格
⑧  03 用户流程
⑨  41 编码规范
⑩  现有代码（最低）
```

**关键结论：代码与规则冲突时，改代码，不是改规则。**

> 唯一例外：若现有代码有明确实现、而文档从未覆盖该边界（属于文档遗漏），**保持代码现状不动**，并按第四节上报，由用户决定。

## 三、工作流（每次会话的标准动作）

### 3.1 开工前

1. 读 `42_DEV_TASKS.md`，确认当前该做哪个 T-xx（看 `43_DEV_STATUS.md` 的进度）
2. 读该任务「涉及文档」一栏列出的全部文档章节
3. 读「涉及文件」一栏列出的每个文件的当前内容，**确认行号是否仍与文档一致**

### 3.2 执行中

4. 只改任务范围内允许改的文件
5. 每改完一个文件，自查是否影响现有调用方（Grep 该函数的引用点）
6. 遇到文档没写的情况 → **停下，上报**，不要自己拍脑袋

### 3.3 完成后

7. 按「完成标准」逐条自测
8. 按「测试方法」执行验证
9. 更新 `43_DEV_STATUS.md`：该任务标记完成 + 追加变更日志一行
10. 按第五节模板汇报

## 四、冲突上报模板（AI-9 的强制格式）

发现任何「文档说的」和「代码实际」不一致，或任务描述含糊，**禁止自行决策**，按下面格式输出并停下：

```markdown
## ⚠️ 冲突上报

**任务编号**：T-P1-4
**文档要求**：
> 引用原文（文件 + 行号 + 原文）

**当前代码**：
> 引用代码（文件 + 行号 + 代码片段）

**冲突点**：
> 一句话说清哪里不一致

**影响范围**：
> 会影响哪些功能 / 哪些文件

**我的建议**（可选，仅供你参考，我不自行执行）：
> 方案 A：……
> 方案 B：……

**等待确认后继续。**
```

**禁止**在没有得到明确答复的情况下，采用「我觉得应该是这样」继续写代码。

- 无 / （有则列出）

## 六、禁止的行为清单（补充细则）

| 禁止 | 说明 |
|---|---|
| 禁止「为了让测试通过」改产品规则 | 例如把 `packageCount` 上限改大来规避上限校验 |
| 禁止添加文档未定义的状态值 | 项目状态只有 5 个（BR-204） |
| 禁止在前端做「唯一的安全校验」 | 后端必须有对应校验（BR 校验位置标「后端」的） |
| 禁止引入 npm 依赖 | 云函数端和网页端都禁止。网页端零框架（hash 路由 + 原生 JS） |
| 禁止修改 `ensureApp()` / `callFn()` / `uploadBlob()` | `web/upload.js` 的传输层，已验证可用（C-1 裁决） |
| 禁止把大图手势从 `gest.wxs` 迁到逻辑层 | 会造成卡顿（架构红线） |
| 禁止在未被告知时执行 `git push` / `git commit` | 提交动作由用户决定 |
| 禁止删除任何现有页面目录 | `project-create` 页明确保留（BR-206） |
| 禁止「顺便」删除看起来没用的字段 | `clientName` 虽只读不写，明确保持不动 |
| 禁止新建文档文件 | 需要新文档先问用户 |

## 七、任务领取规则

1. **严格按 `42_DEV_TASKS.md` 的 P0 → P1 → P2 → P3 顺序**
2. 同一优先级内按 T-Px-1 → T-Px-2 顺序
3. **前置条件未完成的任务，不得开始**
4. 一个任务未完成时，**不得**开始下一个
5. 如果某任务因外部原因（如微信公众平台审核）无法完成，标记 `blocked` 并说明，**跳到下一个不受阻的任务**，不要干等

---

## 八、与用户的交互规则

- **提问前先自己查**：文件路径、字段名、函数签名这类信息，用 Read / Grep 自己确认，不要问用户
- **只在两类事情上问用户**：① 文档冲突（第四节模板）② 产品规则层面的取舍（第五节建议项）
- **不要用泛泛的互联网术语回复**：不说「这个可以这样优化」「体验会更好」，要说「改哪个文件的哪一行，改成什么，带来什么可验证的变化」
- **不要汇报工作量**：不说「我做了大量工作」，直接给改动清单

## 九、自检清单（每次改动后自查）

- [ ] 改动是否都在任务范围内？
- [ ] 有没有「顺手」改了别的东西？
- [ ] 新增的常量是否在 `30` 第一章有定义？
- [ ] 新增的状态值是否在 `31` 有定义？
- [ ] 涉及身份的改动，是否走了 `resolveCaller` 而不是直接取 `OPENID`？
- [ ] 涉及资源访问的，是否做了第二重授权校验（BR-106）？
- [ ] 后端校验是否补齐（不能只有前端校验）？
- [ ] 现有调用方有没有被破坏（Grep 一遍）？
- [ ] `43_DEV_STATUS.md` 是否已更新？
- [ ] 汇报模板是否完整？
