### 1.4 安全模型（当前真实状态）

四道锁（原始文档已移入 `docs/_archive/安全与访问控制.md`；V2 权威版本见 `23_PERMISSION.md`）：

1. **数据库**：`project` / `photo` / `model` / `invite` / `selection` / `admin` 全部权限为「仅管理端可读写」
2. **归属隔离**：所有 project action 走 `ownedProject()`（`project/index.js:465-479`），核对 `ownerOpenid`，摄影师之间互不可见
3. **邀请 token**：`invite.token` 为 22 位 base62 随机串，`< 16` 位直接拒绝（`selection/index.js:434`）
4. **一码一人**：`model.openid` 一旦被某微信认领，其他微信拿同一链接会被拒（`selection/index.js:116-123`）

**权限实现方式值得注意**：`<image>` 无法直用 fileID，所有图片访问必须经过云函数 `cloud.getTempFileURL()` 换取临时链接（`selection/index.js:550-568`，`maxAge = 24h`）。这是成本优化中的重要约束——上一轮「image 直用 fileID」的建议与这条安全模型冲突，最终选了「批量取 + 端上缓存」的保守方案。

## 三、V1 → V2 问题清单

### 3.1 产品层面

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| P-1 | **摄影师不知道「下一步该做什么」** | `project-detail` 是三个区块的罗列（照片 / 模特 / 结果），不区分项目当前处于什么阶段 | 新建项目后，摄影师要靠自己记住流程，才知道该先去复制上传码 |
| P-2 | **模特提交后摄影师无感知** | 全代码无订阅消息、无推送 | 唯一途径是手动刷新页面，体验上「对方做完了，我不知道」 |
| P-3 | **上传流程跨越两个设备，路径最长** | 小程序复制带码网址 → 电脑浏览器粘贴 → 网页生成码 → 5 分钟超时重来 | 这是整条链路里唯一需要「人肉搬运数据」的环节 |
| P-4 | **上传无进度回传** | 摄影师看不到「这个项目的照片传了多少 / 还剩多少」 | `project-detail` 只显示已完成的 `photoCount` |
| P-5 | **模特无法回看自己选了什么** | 无「只看已选」筛选 | 提交前想复查，只能靠记忆在几百张里找 |
| P-6 | **没有容量 / 额度上限** | `usedBytes` 只计量不限制 | 与先前定下的三档额度、加量包商业化设计直接冲突 |
| P-7 | **在线额度的概念没有任何 UI 表达** | `project-detail` 只有一个 `usedText`（`index.ts:130`） | 收费的话用户不知道自己为什么被拦 |

### 4.2 关键结论：竞争优势不在功能多寡

绚篇的商业模式是「**会员订阅 + 交易抽佣 2%**」双轨，后者才是大头。它的多端客户端只是载体，真正的护城河是「选完直接付钱、摄影师不用推销」这个闭环——而这个闭环需要 **企业资质 + 商户号 + ICP 备案**，个人开发者基本堵死。

因此：

> **不要追功能数量。你的差异点是「输出文件名清单」这件事本身——它面向用 Lightroom 自己修图的独立摄影师，他们不需要二销、不需要交付、不需要防截屏，只需要知道模特选了哪几张。**

绚篇面向影楼 / 工作室（要卖钱），我面向自己修图的个人摄影师（要清单）。这是两套完全不同的工作流，不是同一条赛道上的落后版本。

### 4.3 对三个「看起来该有」的功能，逐条回答七问

#### ① 照片留言 / 标记

1. **解决什么问题**：客户想在某张照片上说明「这张要修痘」「这张帮我裁方」
2. **什么场景**：交付前的精修沟通
3. **为什么这样设计**：影楼流程里，客户选中 ≠ 沟通完修图要求，需要第二轮信息传递
4. **没有会怎样**：客户只能通过微信另行发送文件名 + 要求，摄影师人工对应，容易错
5. **我的产品有同样问题吗**：部分有。但个人摄影师的交付通常微信直接沟通，量小
6. **增加什么复杂度**：`selection` 要加 `notes: Record<photoId, string>` 或独立 `note` 集合；模特端要输入框 + 键盘避让；摄影师端要展示与回复
7. **是否值得 V2**：**否，放 V3**。理由：它是「精修交付」的前置能力，而你明确不做精修交付。单独做一半（只有留言没有回复、没有流转）价值不大

#### ② 推荐 / 必选

1. **解决什么问题**：摄影师想引导客户选某些片
2. **什么场景**：套餐含固定张数，摄影师希望客户优先选自己挑好的
3. **为什么这样设计**：保护出品质量，避免客户选出摄影师不满意的片
4. **没有会怎样**：摄影师靠微信口头说明
5. **我的产品有同样问题吗**：有，但个人摄影师通常全程自己控盘
6. **增加什么复杂度**：`photo` 或 `selection` 加 `recommended: boolean[]`；模特端要有视觉区分 + 「一键全选推荐」
7. **是否值得 V2**：**否，放 V3**。这是商业套餐场景的附属功能，非核心链路

#### ③ 照片分组

1. **解决什么问题**：一次拍摄分多套造型/多场景，客户按组浏览
2. **什么场景**：婚纱、写真（多套服装）
3. **为什么这样设计**：几百张平铺无法浏览，分组降低决策负担
4. **没有会怎样**：我的 V1 靠文件名升序 + 无限滚动，500 张要滚 28 屏
5. **我的产品有同样问题吗**：**有，而且这是 V2 最该解决的问题之一**
6. **增加什么复杂度**：`photo` 加 `groupName`，web 端按上层文件夹名自动分组即可（**成本极低**，因为拖拽文件夹上传本来就有 `relPath`）
7. **是否值得 V2**：**值得，但要做轻量版**——不是让用户手动分组，而是**上传时按本地文件夹自动生成组**，模特端一个横向 tab 切换。这个功能的 80% 价值可以用 20% 的成本拿到

> 【待确认】你在实际拍摄中，一次项目是否会分成多个文件夹（如「第一套」「第二套」）？这决定了分组是直接做还是需要别的设计。

## 五、文档 / 设计意图 vs 代码实现：差异清单

这一节是给后续 Coding AI 的「冲突上报」基准。**凡在此列出且未标记为「已解决」的条目，Coding AI 不得自行修改代码。**

### D1 【冲突 · 需拍板】提交后是否锁定

| | 内容 |
| --- | --- |
| **产品规则（此前约定）** | 模特提交后锁定，如需修改必须由摄影师解锁 |
| **当前代码** | `client-select/index.wxml:9-18` 在提交成功页直接提供「继续调整」按钮；点击执行 `setData({ phase: 'ready' })`，**不调用任何后端接口，不校验摄影师是否解锁** |
| **后端状态** | `selection.locked` 依然是 `true`，且后端**没有**任何「禁止 `saveSelection`/`submitSelection` 当 `locked === true`」的校验（`selection/index.js:310-352`） |
| **实际效果** | 模特可以无限次自行修改并重新提交；`resetLock` 这个摄影师权限完全失去意义 |
| **建议** | 二选一：<br>① **维持规则**：后端 `saveSelection` / `submitSelection` 加 `locked` 拦截，前端去掉自助解锁入口，模特修改必须等摄影师 `resetLock`<br>② **改规则**：明确「提交后可随时自助调整，最新版覆盖旧版」，那就删除 `resetLock` action，避免功能冗余 |
| **我的倾向** | ①。理由：老板只有一个，摄影师需要拿到确定的结果才能开始修图。自助改会让摄影师永远不知道哪一版是最终版 |

### D2 【冲突 · 需拍板】`resetLock` 是否清空选择

| | 内容 |
| --- | --- |
| **前端文案** | `selection-result/index.ts:120`：「会**清空**她当前的选择，她可以重新选一次」 |
| **后端实现** | `selection/index.js:411, 414`：`const keep = sel.photoIds`，写入 `photoIds: keep` —— **保留** |
| **实际效果** | 摄影师点「重新开放」，模特看到的是「之前选的都还在，在此基础上继续挑」 |
| **建议** | 改为文案跟随实现：「保留她已选的 N 张，她可在此基础上继续调整」。或反过来改成真清空（需先确认哪个是你要的） |
| **我的倾向** | 保留实现、改文案。保留选择更符合「多加几张」的真实场景 |

### D3 【冲突】项目存在与实际使用无关的状态值

| | 内容 |
| --- | --- |
| **类型定义** | `types/index.ts:2-10`：`DRAFT / UPLOADING / SELECTING / SELECTION_SUBMITTED / COMPLETED / EXPIRED / ARCHIVED` 共 7 个 |
| **实际写入的值** | 仅 5 个：`DRAFT`（create）、`UPLOADING`（photo 登记 / extend 恢复）、`SELECTING`（guardModel、resetLock、updateModelSummary）、`SELECTION_SUBMITTED`（updateModelSummary）、`ARCHIVED`（archive） |
| **从不写入** | `COMPLETED`（无人写）、`EXPIRED`（无人写，页面靠 `expireAt < now` 现算） |
| **建议** | V2 状态机重设计时，把 `COMPLETED` 删掉，把「过期」明确定义为一个**派生状态**（由 `expireAt` 计算，不落库），而不是一个存储状态 |

### D4 【缺陷】`project.previewSpec` 是死字段，画质实际由上传页操作员决定

| | 内容 |
| --- | --- |
| **设计意图** | 项目创建时写入 `previewSpec`（`project/index.js:101`），似乎是「这个项目的画质」 |
| **实际路径** | web 上传页从自己的下拉框取值（`upload.js:281` `currentSpec()` → `PRESETS` 或自定义），**从不读取 `project.previewSpec`**；`registerPhoto` 也**从不回写** `project.previewSpec` |
| **后果** | 当前默认画质靠两个地方的「巧合」保持一致（`project/index.js:101` 和 `web/upload.js:28` 都写了 1600/0.75）。任何一边改动都会静默失真；`watermarkText` 字段同样从未被 web 端读取 |
| **建议** | 二选一：<br>① 承认「画质是上传时的选择」→ 删除 `project.previewSpec`，改为在 `photo` 上记录实际使用的 spec<br>② 承认「画质是项目属性」→ 上传页第 2 步先拉一次 `project.previewSpec` 作为默认值，并在后端校验一致性 |

### D5 【待确认】「多摄影师」边界

当前 `admin.bind` 是零门槛的——**任何人打开小程序点一下「我是摄影师」就能成为摄影师**（`admin/index.js:36-44`）。这在自用场景下合理（你自己），但如果开源出去，`admin` 集合会长出一堆陌生 openid。虽然 `ownerOpenid` 隔离了数据互不可见，但这与之前讨论过的「三档会员 / 在线额度」是两套完全不同的事。

> 【待确认】开源版是否要保留「人人可开通摄影师」？还是加一个开关（默认自用模式，部署者自行决定是否加口令）？

### D6 【待确认】`usedBytes` 是真相还是估算

`usedBytes` 由 `photo.previewBytes + photo.thumbBytes` 累加（`photo/index.js:175`），重传时按差值调整（`:151-159`），归档时重算为 thumb 总量（`project/index.js:184`）。

但它与「云存储上的真实占用」存在系统性偏差：
- 每项目还有 **1~5 个二维码 PNG**（`project/index.js:440` 上传，却从未计入 `usedBytes`）
- 删除失败的文件（`deleteFiles` 返回 `failed`）不会被扣减

> 【待确认】如果 `usedBytes` 要用于收费（加量包），建议先跑一次真实对账脚本，确认偏差在可接受范围

## 六、初步判断：V2 的主线是什么

基于上面的盘点，我的初步感受是——**V1 的功能骨架已经完整，「摄影师上传 → 客户打开 → 浏览 → 选择 → 提交 → 查看结果」这条链路每一环都有东西。** 真正缺的不是新功能，而是四处：

1. **闭环感缺失**（Section 3.1）：链路每一步都做完了，但没人告诉参与者「下一步是什么」和「对方完成了吗」
2. **摄影师网页端几乎不存在**（`web/` 现在只是一个上传页，不是控制台）：这是你截图里绚篇左边那半边，目前完全空白
3. **两个规则缺陷必须修**（D1、D2）：不改的话后续 AI 会在错误的地基上盖楼
4. **开源阻塞项**（T-1、T-2）：硬编码与私有配置

其余都属于「可以锦上添花，但没有也不致命」。

### R-4 附：上传页画质预览（新增功能）

**目的**：让摄影师在上传前亲眼看到各档画质「到底有多糊」，再决定选哪档。

| 项 | 规格 |
|---|---|
| 触发时机 | 上传向导第 2 步（已选文件、尚未开始上传） |
| 样张来源 | 默认取**已选文件的第 1 张**；提供「换一张」让用户从已选文件中另挑（建议挑人像眼部等细节处） |
| 生成方式 | **纯浏览器本地**，用 `createImageBitmap` + `OffscreenCanvas` 缩放并 `toBlob(type, quality)`，复现四档参数。**不上传、不消耗任何云资源** |
| 对比界面 | 左右滑块拖动对比（默认 标准 vs 高清），可切换对比对象；**必须支持 100% 原始像素放大查看**（糊不糊只有在 1:1 下才看得出来） |
| 每档标注 | 长边像素 / quality / 单张预估体积 / **「你这批 N 张 ≈ XXX MB」**（与在线额度联动显示） |
| 四档参数 | 标准 1600/0.75（默认）、高清 2048/0.82、高清 Pro 2880/0.90、原画质 4096/0.92 |

> 注意：浏览器 canvas 的 JPEG 编码质量与云端的 sharp 不完全一致，预览体积是**估算**，允许 ±15% 偏差，界面上标注「预估」。

### R-7 附：`usedBytes` 方案（计数器 + 关键点校准）

- **日常读**：用 `project.usedBytes` 增量计数器（上传 `inc`、归档/删除 `inc` 负值），避免每次全表聚合。
- **校准**：在以下三个低频节点，用 `photo` 表聚合（`sum(previewBytes + thumbBytes)`）**重算并覆盖**计数器 —— ① 项目归档时；② 删除照片后；③ 续期（extend）时。
- **补齐遗漏**：邀请二维码 PNG（`project/index.js:440`）目前未计入，改为生成后回写 `usedBytes`。
- **删除失败**：`deleteFiles` 返回 `failed` 时不扣减，并写日志（现状如此，保持）。
- 收费/加量包属于开源阶段事项，本轮只要求计数器可用、可校准。
