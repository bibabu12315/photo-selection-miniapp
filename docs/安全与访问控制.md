# 安全与访问控制设计

> 回答一个问题：**没有登录体系，模特 B 能不能看到模特 A 的照片？**
> 结论：正常情况下不能，但前提是下面四道锁全部做对。

---

## 一、隔离模型：靠 token，不靠账号

每个项目有独立的 `accessToken`（22 位 base62，约 131 bit 熵）。进入项目必须携带 token，token 不可枚举、不可猜测。

```
模特 B 手里只有「项目 B 的 token」
   ↓
云函数用 token 查出 projectId = B
   ↓
只返回 B 的照片
```

B 拿不到 A 的 token，就查不到 A 的项目——**不管她有没有账号，都一样**。所以"没有登录体系"本身不等于"没有隔离"。

**真正危险的不是有没有登录，而是下面四件事有没有做对。**

---

## 二、四道必须做对的锁

### 锁 1：数据库权限必须锁死（最大的漏洞）

CloudBase 数据库如果停留在默认的「所有用户可读」，那么任何人在小程序里执行一句 `db.collection('project').get()` 就能拿到你全部项目，token 形同虚设。

**要求：**

- 数据库权限设为 **「仅管理端可读写」**
- 前端（小程���端、Web 端）**一律不直接读库**，所有数据经云函数返回
- 每个读接口都要校验调用者身份（管理员 / 有效 token）

这是四道锁里最重要的一道，也是最容易在"先跑通再说"时被忽略的一道。

### 锁 2：每次下发图片链接都要校验 token

云存储设为「仅创建者可读写」，图片 URL 由云函数以 admin 权限调 `getTempFileURL` 下发。但**下发前必须校验 token 属于该项目**：

```
getProjectPhotos(token, projectId, page)
   ↓
token → projectId_A
   ↓
projectId_A == 请求的 projectId ？
   ├── 是 → 下发
   └── 否 → 拒绝
```

否则模特 A 可以拿自己的 token 去请求 `projectId = B`，照样拿到 B 的图。**参数里的 projectId 永远不能信，只能信 token 推导出来的那个。**

### 锁 3：管理员绑定不能被抢占（修订上一版方案）

上一版写的"第一个不带 token 打开的人自动成为管理员"**有漏洞**：若模特先于摄影师打开，她会被绑成管理员，进而看到所有项目。

**改为以下任一方案：**

| 方案 | 做法 | 评价 |
|---|---|---|
| A（推荐） | 云函数环境变量设 `ADMIN_BIND_KEY`，首次打开需输入该口令才绑定管理员 | 零 UI 成本，彻底堵死抢占 |
| B | 环境变量 `ADMIN_OPENID` 硬编码 | 最稳，但需先从日志里取出自己的 openid 再回填 |
| C | 自动绑定（原方案） | **不采用** |

另外，`bindAdmin` 云函数必须校验：**管理员一旦绑定，不允许再次绑定**，重置只能在 CloudBase 控制台手动改数据库。

### 锁 4：一码一人（替代登录体系的低成本方案）

账号体系相比 token 模型，唯一多解决的问题是**「模特 A 把链接转发给别人」**。这个问题不需要账号，用 openid 绑定就能解决：

```
模特首次打开（带 token）
   ↓
静默 wx.login → openid
   ↓
云函数校验
   ├── token 无效 / 项目过期        → 拒绝
   ├── selection.boundOpenid 为空   → 写入 boundOpenid，放行
   ├── boundOpenid == 当前 openid   → 放行
   ├── 当前 openid == 管理员        → 放行（摄影师自己预览）
   └── 其他                         → 拒绝：「此链接已被其他微信账号使用」
```

- 微信 openid 在同一小程序内**永久固定**，模特换手机、重装微信都不影响。
- 摄影师端提供「解绑」按钮，应对模特换微信账号的情况。
- 成本约 20 行云函数代码，效果接近登录体系。

**副作用**：一个链接只能一个人用。若需要两个人看同一个项目（模特 + 朋友），V1.1 再考虑生成多个 token。

---

## 三、能防住 vs 防不住

| 场景 | 是否防住 | 手段 |
|---|---|---|
| 模特 B 猜到/枚举 A 的项目 | 防住 | 22 位随机 token |
| 模特 B 改请求参数读别人的库 | 防住 | 锁 1 + 锁 2 |
| 模特 B 先打开小程序抢占管理员 | 防住 | 锁 3 |
| 模特 A 把链接转发给 B | 防住 | 锁 4（一码一人） |
| 摄影师把 A 的码错发给 B | **防不住** | 人为错误 |
| 二维码图片被发到群里/朋友圈 | **防不住** | 谁扫都能进，慎用图片二维码 |
| 模特自己截图外传 | **防不住** | 只能靠 preview 水印做心理约束 |
| 项目过期后继续访问 | 防住 | `expireAt` 校验 |

**建议**：优先用「分享小程序卡片」而不是二维码图片。卡片是点对点发给模特的，不会像图片那样被随手转发到群里。

---

## 四、额外的加固项（低成本）

1. **链接可重置**：摄影师端提供「重新生成链接」，旧 token 立即失效。怀疑泄露时一键处理。
2. **token 不落盘**：token 只走页面参数，不写入 `wx.setStorageSync`，避免换项目时残留串档。
3. **水印**：preview 固定右下角半透明水印，不能阻止截图，但能抑制二次传播。
4. **项目有效期 30 天**：过期后 token 自动失效，缩小暴露窗口。
5. **访问日志**：记录 token 的首次使用时间和 openid，出问题能追溯。

---

## 五、结论

**不需要做账号体系。** 四道锁加起来不到 100 行代码，就能覆盖账号体系能解决的绝大部分问题。

真正防不住的三项（发错码、码发群里、截图外传）**本来就不是技术问题**——就算做了登录，摄影师把 A 的项目分享给 B，B 登录后照样看得到。所以增加登录体系的边际收益很低，不值得为它引入注册、找回、多端同步这一整套复杂度。
